# Вимоги до agent harness проєкту RecipeHub

## 1. Мета harness

Harness має прискорити розробку бекенду RecipeHub (Java 21, Spring Boot 3, PostgreSQL) засобами Claude Code. Для цього він забезпечує три речі:

- **що агент знає** — актуальний стан застосунку, прийняті архітектурні рішення та конвенції проєкту;
- **що агент уміє** — формалізовані процедури для типових повторюваних задач розробки;
- **чого агент не може** — обмеження, що захищають кодову базу, базу даних і секрети від помилкових автономних дій.

Архітектурні рішення та вимоги визначає розробник. Агент виступає акселератором: генерує типовий код і тести, перевіряє відповідність конвенціям і допомагає аналізувати збої. Harness не є частиною бізнес-логіки застосунку.

## 2. Джерела даних

На старті проєкту єдиним джерелом є документація вимог. Решта джерел з'являється в процесі розробки й підключається до harness у міру появи.

| Джерело | Розташування | Коли з'являється | Що дає агенту | Доступ агента |
|---------|--------------|------------------|---------------|---------------|
| Документи вимог | `ЗАВДАННЯ.md`, `docs/*.md` | ПР № 1 | Обсяг застосунку, функціональні вимоги, архітектурні принципи | Файлова система (репозиторій застосунку) |
| Проєктні інструкції | `CLAUDE.md` | Початок розробки | Конвенції коду, правила API, структура модулів, команди збірки | Автоматично завантажується Claude Code |
| Вихідний код | `src/main/java/...` | Перша ітерація розробки | Поточна структура модулів, приклади реалізації, стиль коду | Файлова система |
| Схема БД | `src/main/resources/db/migration/` | Перша сутність | Актуальна структура таблиць, історія змін схеми | Файлова система |
| Тести та результати збірки | `src/test/java/...`, вивід `./gradlew test`, `build/reports/tests/` | Перша функція з тестами | Покриття функціональності, причини падіння тестів | Файлова система, bash |
| Конфігурація збірки та інфраструктури | `build.gradle`, `compose.yaml`, `application.yml` | Створення проєкту | Залежності, версії, параметри запуску | Файлова система |
| Специфікація API | `/v3/api-docs` (генерується springdoc) | Перший ендпоінт | Фактичний контракт API для перевірки узгодженості | bash (запит до запущеного застосунку) |
| Історія версій | git-репозиторій застосунку | Перший коміт | Хронологія змін, мотивація рішень у повідомленнях комітів | bash (`git log`, `git diff`) |
| База знань (vault) | Окремий git-репозиторій (Obsidian) | ПР № 2 | Опис модулів і сутностей, архітектурні рішення (ADR), глосарій домену, зв'язки між поняттями | **Лише через MCP-сервер конектора** (ПР № 3) |

### Правила для джерел даних

- Повідомлення комітів пишуться за форматом Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`), щоб історія версій була машинозчитуваним джерелом.
- Кожне суттєве архітектурне рішення фіксується в базі знань як окрема нотатка (ADR).
- База знань фізично відсутня в робочій директорії агента. Читання (retrieval) і запис (ingestion) виконуються лише через типізовані інструменти MCP-сервера.
- CI/CD-автоматизація в обсяг курсу не входить. Роль журналів збірки виконують вивід `./gradlew build` / `./gradlew test` і HTML-звіти Gradle.

## 3. Цільові задачі агента

| ID | Задача | Режим | Цінність | Реалістичність у межах семестру |
|----|--------|-------|----------|---------------------------------|
| T-1 | **Генерація каркасу модуля.** За описом сутності агент створює повний вертикальний зріз: Flyway-міграцію, JPA-сутність, DTO, репозиторій, сервіс, контролер з префіксом `/api/v1`. | Напівавтономний (розробник затверджує зміни) | Модулі `recipe`, `tag`, `favorite` та майбутні модулі з беклогу мають однакову структуру, тож рутинна частина роботи скорочується в рази | Висока: шаблон чітко визначений архітектурними принципами, результат легко перевірити збіркою |
| T-2 | **Генерація тестів.** Для нового або зміненого коду агент пише unit-тести сервісів (JUnit 5, Mockito) та інтеграційні тести ендпоінтів (MockMvc, Testcontainers), включно з перевірками доступу. | Напівавтономний | Тести пишуться для кожної функції, а не «колись потім», і фіксують критерії успішності з вимог | Висока: результат вимірюваний — тести компілюються і проходять `./gradlew test` |
| T-3 | **Рев'ю коду на відповідність конвенціям.** Агент перевіряє зміни за чеклистом проєкту: префікс `/api/v1`, DTO замість сутностей у контролерах, UUID, формат помилок `ProblemDetail`, пагінація, перевірка авторства, відсутність редагування застосованих міграцій. | Автономний (лише читання, результат — звіт) | Архітектурні правила дотримуються стабільно, що критично для подальшого підключення мобільного клієнта | Висока: чеклист формалізується як skill, дія не змінює код |
| T-4 | **Аналіз збоїв збірки та тестів.** Агент запускає `./gradlew test`, аналізує вивід і звіти, визначає причину падіння та пропонує виправлення. | Напівавтономний (виправлення лише після підтвердження) | Швидше виправлення помилок, особливо в незнайомих зонах (Spring Security, Flyway, Testcontainers) | Середня: причини збоїв різноманітні, але вивід Gradle структурований і відтворюваний |

Задачі впорядковано за етапами курсу: T-1 і T-2 застосовуються з перших ітерацій розробки ядра, T-3 стає корисною після накопичення коду, T-4 — під час роботи з інтеграційними тестами та безпекою.

## 4. Guardrails (первинний перелік категорій дій)

Нижче наведено категорії на рівні типів операцій. Конкретні правила та їх технічна реалізація через hooks Claude Code — предмет ПР № 4.

### Allow — дозволено без підтвердження

Низький ризик, дія не змінює стан проєкту або повністю оборотна.

- Читання файлів репозиторію застосунку та пошук по коду.
- Запуск збірки та тестів (`./gradlew build`, `./gradlew test`).
- Перегляд стану git (`git status`, `git diff`, `git log`).
- Читання бази знань через інструменти retrieval MCP-сервера.
- Запити до локально запущеного застосунку (наприклад, отримання `/v3/api-docs`).

### Warn / Require approval — потрібне підтвердження розробника

Середній ризик або обмежена оборотність.

- Створення та редагування файлів у `src/main` і `src/test`.
- Створення **нових** Flyway-міграцій.
- Зміна залежностей і конфігурації збірки (`build.gradle`).
- Зміна локальної інфраструктури та налаштувань (`compose.yaml`, `application.yml`).
- Створення комітів і гілок.
- Запис у базу знань через інструменти ingestion MCP-сервера.
- Запуск довільних shell-команд поза переліком Allow.

### Block — заборонено безумовно

Високий ризик або незворотні наслідки.

- Редагування чи видалення вже застосованих Flyway-міграцій.
- Читання та зміна файлів із секретами (`.env`, ключі, облікові дані).
- Push у гілку `main`, force push, переписування історії (`git reset --hard`, `git rebase` опублікованих комітів).
- Масове видалення файлів і директорій (`rm -rf` тощо).
- Знищення даних БД: `DROP` / `TRUNCATE`, видалення Docker-томів з даними.
- Зміна конфігурації самого harness (`.claude/settings.json`, hook-скрипти) з боку агента.
- Вимкнення або видалення тестів для проходження збірки (`@Disabled`, видалення тест-класів).
- Доступ до репозиторію бази знань в обхід MCP-сервера.

## 5. Розміщення компонентів harness

Усі компоненти, крім бази знань, зберігаються в репозиторії застосунку й версіонуються разом із кодом.

```
recipehub/                     # репозиторій застосунку
├── CLAUDE.md                  # проєктні інструкції та конвенції
├── .mcp.json                  # реєстрація MCP-сервера конектора (ПР № 3)
├── .claude/
│   ├── settings.json          # hooks і дозволи — guardrails (ПР № 4)
│   ├── hooks/                 # скрипти перевірок (ПР № 4)
│   ├── skills/                # процедури для задач T-1 – T-4 (ПР № 5)
│   └── agents/                # subagents для оркестрації (ПР № 6)
├── mcp-server/                # MCP-сервер конектора до бази знань (ПР № 3)
├── docs/
└── src/

recipehub-vault/               # окремий репозиторій бази знань (ПР № 2)
```

## 6. Критерії оцінювання harness

Первинний набір метрик для порівняльного тестування в ПР № 7:

- **Success rate** — частка задач T-1 – T-4, виконаних агентом так, що збірка і тести проходять без ручних виправлень.
- **Відповідність конвенціям** — кількість порушень чеклиста T-3 у коді, згенерованому агентом.
- **Порушення guardrails** — кількість спроб заблокованих і попереджуваних дій.
- **Hallucination rate** — частка відповідей з посиланнями на неіснуючі класи, методи, ендпоінти чи рішення, відсутні в коді та базі знань.
