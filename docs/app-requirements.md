# Вимоги до застосунку RecipeHub

## 1. Загальний опис

**RecipeHub** — REST API бекенд для зберігання та поширення кулінарних рецептів. Користувачі створюють власні рецепти, керують їх видимістю (приватні або публічні), переглядають публічні рецепти інших користувачів і зберігають їх в обране.

Вимоги поділено на дві частини:
- **обсяг курсу** (розділ 3) — мінімальний завершений бекенд, який реалізується протягом семестру;
- **беклог розвитку** (розділ 4) — можливості, які не входять у курс, але архітектура дозволяє додати їх пізніше без переробки. Головна з них — підтримка майбутнього мобільного застосунку.

Інтерфейс користувача в обсяг курсу не входить: взаємодія відбувається через REST API (Swagger UI, автоматичні тести).

## 2. Цільові користувачі

- **Домашні кулінари**, які хочуть мати впорядковану особисту колекцію рецептів.
- **Користувачі, що діляться рецептами** з іншими людьми через публічну стрічку.
- **Майбутній мобільний клієнт** (iOS / Android) — основний споживач API після завершення курсу.

## 3. Функціональні вимоги (обсяг курсу)

| ID | Вимога | Опис |
|----|--------|------|
| FR-1 | Реєстрація та вхід | Реєстрація за email і паролем, вхід з отриманням JWT-токена. Захищені ендпоінти доступні лише з валідним токеном. |
| FR-2 | CRUD рецептів | Створення, перегляд, редагування та видалення власних рецептів. Рецепт містить: назву, опис, інгредієнти (назва, кількість, одиниця виміру), кроки приготування, час приготування, кількість порцій. |
| FR-3 | Теги | Призначення рецепту одного або кількох тегів («сніданок», «веган», «десерт»). |
| FR-4 | Пошук і фільтрація | Пошук рецептів за назвою, тегом та інгредієнтом, з пагінацією. |
| FR-5 | Видимість рецепта | Статус `PRIVATE` (бачить лише автор) або `PUBLIC` (бачать усі). |
| FR-6 | Стрічка публічних рецептів | Перегляд публічних рецептів інших користувачів із пагінацією. |
| FR-7 | Обране | Додавання публічних рецептів інших користувачів до списку «Обране» та видалення з нього. |
| FR-8 | Масштабування порцій | Отримання рецепта з перерахованою кількістю інгредієнтів для заданої кількості порцій. |

### Етапність реалізації

- **Ядро:** FR-1 – FR-4
- **Соціальна частина:** FR-5 – FR-7
- **Додаткова логіка:** FR-8

## 4. Беклог розвитку (поза обсягом курсу)

Ці можливості не реалізуються в межах курсу. Вони зафіксовані, щоб архітектурні рішення курсу їм не суперечили.

| ID | Можливість | Що для неї вже закладено |
|----|-----------|--------------------------|
| BL-1 | Мобільний застосунок | Stateless API, версіонування, OpenAPI-контракт, єдині формати даних (розділ 6) |
| BL-2 | Refresh token і тривалі сесії | Автентифікація винесена в окремий модуль `auth`, заміна схеми токенів не зачіпає інші модулі |
| BL-3 | Фото рецептів | Рецепт ідентифікується UUID, тож фото можна прив'язати окремою сутністю |
| BL-4 | Поширення за посиланням і deep links | UUID як ідентифікатори, безпечні для використання в посиланнях |
| BL-5 | Розгортання на сервері або в хмарі | Інфраструктура вже описана через Docker Compose, налаштування (БД, секрети) передаються через змінні середовища |
| BL-6 | Коментарі, рейтинги, підписки на авторів | Модульна структура за функціональними областями (розділ 6) |

## 5. Нефункціональні вимоги

**Безпека**
- Паролі зберігаються у вигляді хешу (BCrypt).
- Автентифікація через JWT з обмеженим терміном дії.
- Користувач може змінювати та видаляти лише власні рецепти.
- Секрети (JWT secret) не зберігаються в репозиторії, а передаються через змінні середовища.
- Вхідні дані валідуються (Bean Validation).

**Продуктивність**
- Час відповіді типових запитів не більше 500 мс на локальному середовищі.
- Списки повертаються з пагінацією (за замовчуванням 20 елементів).

**Якість**
- Бізнес-логіка покрита unit-тестами, ключові ендпоінти — інтеграційними тестами на реальному PostgreSQL (Testcontainers).
- Схема БД змінюється лише через Flyway-міграції, написані під PostgreSQL. Застосовані міграції не редагуються: зміни вносяться лише новими міграціями.
- Документація API генерується автоматично (Swagger UI).

## 6. Архітектурні принципи

Принципи обрано так, щоб вони нічого не коштували під час курсу, але їх було б дорого додавати пізніше.

**Структура за функціональними модулями.** Код групується за областями, а не за технічними шарами. Нова функція додається як новий пакет і не зачіпає існуючі:

```
com.recipehub
├── auth/        # реєстрація, вхід, JWT
├── recipe/      # рецепти, інгредієнти, масштабування
├── tag/         # теги
├── favorite/    # обране
└── common/      # обробка помилок, пагінація, конфігурація
```

Усередині кожного модуля — шари `controller` → `service` → `repository`.

**Правила API:**
- усі ендпоінти мають префікс `/api/v1/...`;
- API не зберігає сесій, токен передається в заголовку `Authorization: Bearer <token>`;
- контролери приймають і повертають лише DTO, а не JPA-сутності;
- ідентифікатори — UUID;
- дати в ISO-8601, UTC;
- помилки повертаються в єдиному форматі `ProblemDetail` (RFC 7807) через глобальний обробник;
- пагіновані відповіді мають однакову структуру.

**Конфігурація та запуск:**
- уся локальна інфраструктура (PostgreSQL) описана в `compose.yaml` у корені репозиторію, контейнер піднімається автоматично при `./gradlew bootRun`;
- параметри підключення до БД і секрети задаються через змінні середовища, у репозиторії зберігаються лише значення для локальної розробки;
- єдина передумова для запуску проєкту: встановлені JDK 21 і Docker.

## 7. Технологічний стек

| Шар | Технологія |
|-----|-----------|
| Мова | Java 21 |
| Фреймворк | Spring Boot 3 (Web, Data JPA, Security, Validation) |
| Збірка | Gradle (Groovy DSL, Gradle Wrapper) |
| База даних | PostgreSQL 16 |
| Локальна інфраструктура | Docker, Docker Compose (`compose.yaml`), автозапуск через `spring-boot-docker-compose` |
| Міграції | Flyway |
| Документація API | springdoc-openapi (Swagger UI) |
| Тестування | JUnit 5, Mockito, Spring MockMvc, Testcontainers (PostgreSQL) |
| Контроль версій | Git, GitHub |

## 8. Обрана агентна IDE

**Інструмент:** Claude Code (CLI, за потреби з плагіном для IntelliJ IDEA або VS Code).

**Обґрунтування:**

| Критерій | Підтримка в Claude Code |
|----------|-------------------------|
| Підключення MCP-серверів | Так: реєстрація через `claude mcp add` або проєктний файл `.mcp.json`. Використовується для конектора до бази знань (ПР № 3). |
| Виконання bash-команд у робочій директорії | Так: агент запускає `git`, `./gradlew build`, `./gradlew test` безпосередньо в репозиторії застосунку. |
| Проєктні інструкції та конвенції | Так: файл `CLAUDE.md` у корені репозиторію з архітектурними правилами та конвенціями проєкту. |
| Механізм hooks | Так: `PreToolUse` / `PostToolUse` hooks у `.claude/settings.json`. `PreToolUse` може заблокувати дію, що дозволяє технічно реалізувати guardrails (ПР № 4). |
| Skills | Так: кастомні skills у `.claude/skills/` для формалізованих процедур (ПР № 5). |
| Оркестрація | Так: subagents у `.claude/agents/` для розподілу ролей (ПР № 6). |
| Зручність роботи з Java / Spring Boot | Агент працює з Gradle через CLI і не залежить від IDE, тому код можна паралельно редагувати в IntelliJ IDEA. |

Уся конфігурація Claude Code (`CLAUDE.md`, `.claude/`, `.mcp.json`) зберігається в репозиторії застосунку і версіонується разом із кодом.

## 9. Критерії успішності

Функцію вважають реалізованою, якщо:
- ендпоінт задокументовано в Swagger UI і він відповідає правилам API (розділ 6);
- для нього є автоматичні тести, що проходять (`./gradlew test`);
- поведінка відповідає опису у функціональних вимогах, включно з перевірками доступу (чужий приватний рецепт недоступний, чужий рецепт не можна змінити).
